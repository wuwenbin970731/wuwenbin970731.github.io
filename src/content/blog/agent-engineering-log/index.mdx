Agent 项目最容易膨胀的地方，是一开始就讨论“它能做什么”。
我更喜欢先写清楚“它不能乱做什么”。

## 约束优先

一个可维护的 Agent 至少要回答这些问题：

- 哪些动作必须确认？
- 哪些状态要持久化？
- 哪些失败可以自动重试？
- 哪些失败必须交还给用户？
- 工具输出和用户指令冲突时谁优先？

这些问题听起来不如模型能力酷，但它们决定了系统是否能长期运行。

## 状态要少，但要准

我会把状态分成三层：

1. 当前任务状态。
2. 用户长期偏好。
3. 外部系统事实。

第一层可以频繁更新，第二层需要谨慎写入，第三层最好每次使用前重新验证。

## 失败处理

失败处理不是最后补的异常分支，而是 Agent 设计的一部分。
比如工具调用失败时，系统应该知道：

- 是否可以换一个工具。
- 是否可以降级为只读分析。
- 是否需要用户授权。
- 是否应该停止，避免造成副作用。
